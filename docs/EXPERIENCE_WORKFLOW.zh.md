# Jumper 完整体验开发流程

[项目指南](PROJECT_GUIDE.zh.md) · [English](EXPERIENCE_WORKFLOW.md)

这是把 Jumper 的外观、场景、动作和物理交互组合为一个完整作品的项目级方案。它连接两个独立
版本化的仓库，但不会假装它们共用同一个运行时：

- [jumper-design](https://github.com/KingKongRobotics/jumper-design) 生成仅用于显示的外观包
  `.skin` 和环境包 `.map`。
- 本仓库训练和验证动作、定义控制与状态切换，并把策略和 controller 打包为 `.app`。

开始一个包含多个部分的体验前，先读本文；执行每个阶段时，再遵守对应仓库自己的工作流。

## 交付的是一组产物，不是虚构的统一大包

一个完整体验由以下版本化产物组成：

| 产物 | 归属 | 它证明什么 |
|---|---|---|
| 创意简报和故事板 | 项目 | 角色、世界、交互和演出顺序已经明确。 |
| `<appearance>.skin` | Design | 完整的仅显示机器人外观通过包检查和视觉验收。 |
| `<environment>.map` | Design | 地形、道具、出生点和默认显示机器人通过包检查与 MuJoCo 加载。 |
| 训练 checkpoint 和验证记录 | Train | 每个学习动作通过自己的物理与统计验收门槛。 |
| `<experience>.app` | Train/deploy | 策略、契约、控制、controller 构建和手册组成可加载的运行包。 |
| 证据报告和视频 | 项目 | 结果、失败、辅助机制和未验证边界可见且可复现。 |

不要发明一个把 `.skin`、`.map` 和 `.app` 合并起来的容器。三种格式的消费者和兼容规则不同。
体验记录必须保存两个仓库的准确 commit 和各产物 SHA-256。

## 不可违反的集成边界

1. Train 没有 `.skin` 加载器。皮肤在 Design 中验证和预览，不是训练输入。
2. 导入的 `.map` 在 Train 中仅用于回放；并行训练使用可复制的内置场景。
3. Train 导入地图回放时保留任务自己的机器人和 controller，不会静默替换为地图内嵌的显示机器人。
4. Design 包通过 schema 和 MuJoCo 加载，不等于通过制造适配、策略性能或实机安全验证。
5. 不得静默调和 Design 与 Train 的机械差异。记录 profile、机器人版本和两个 commit，再明确处理差异。
6. 仿真成功不等于板端、真实电机总线或实物载荷验证成功。

## 阶段 0——定义体验契约

生成资产或训练前先写简报：

- 角色和选定的视觉方向；
- 场景、尺度、地形、道具和出生点；
- 按顺序排列的故事节点；
- 每个节点需要的动作；
- 哪些交互必须是物理交互；
- 允许的操作者控制与中断行为；
- 可测量的成功条件；
- 目标仿真器、宿主和实机边界；
- 最终视频与报告要展示什么。

每一种交互必须归为以下一类：

- **物理交互**——结果由碰撞、摩擦和策略/controller 运动决定；
- **操作者择时**——由人选择时机，但产生的动作本身是真实的；
- **剧情辅助**——使用附着、写位姿、动画触发或其他非物理手段。

剧情辅助只有在界面、视频和报告中明确标注时才可以使用，且不得计入物理成功率。

**阶段门槛：**简报、顺序、产物归属和验收指标已经达成一致。

## 阶段 1——选择外观

使用 Design 当前说明：

- [Design AGENTS.md](https://github.com/KingKongRobotics/jumper-design/blob/main/AGENTS.md)
- [Design 工作流](https://github.com/KingKongRobotics/jumper-design/blob/main/docs/workflow.md)
- [内容包协议](https://github.com/KingKongRobotics/jumper-design/blob/main/docs/content-packages.md)

新外观必须先展示有明显差异的候选方案，等待用户明确选择，再决定建模服务或生成几何。记录选中
参考、用户真实确认和不可变哈希。用户明确选定复用某个现有设计，也算通过这一门槛。

**阶段门槛：**一个外观已被明确选中，参考证据已经记录。

## 阶段 2——制作并验证皮肤

在独立的 `jumper-design` checkout 和虚拟环境中：

1. 组装完整机器人，而不是只做一个装饰外壳；
2. 仅显示外观不得改变碰撞或物理参数；
3. 导出当前显示格式（本文编写时为 `.skin/3`）；
4. 使用选定的可信机器人 profile 和 `--mujoco` 运行 `verify-package`；
5. 检查真实的正面、侧面、背面、整机彩色和灰色几何渲染；
6. 检查轮廓、比例、配色、特征细节和动作间隙；
7. 记录 Design commit 和最终压缩包 SHA-256。

打印、切片和物理适配是独立工程。仅显示皮肤不能被描述为已经适配的可打印外壳。

**阶段门槛：**包验证和视觉验收都通过。

## 阶段 3——制作并验证场景

定义尺度、地形、道具、挑战目标、出生点和镜头要求。在 Design 中制作场景并导出当前 `.map`
格式（本文编写时为 `kk-scene-package/2`）。包含经过验证的默认显示机器人和明确出生点。使用可信
profile、所需 capability 和 `--mujoco` 完成包验证。

检查：

- 机器人和道具的尺度；
- 碰撞几何和稳定支撑；
- 出生间隙和可通行路径；
- 灯光、摄像机和最终构图；
- 挑战尺寸是否在动作实测能力内；
- 外部资产的来源和许可证。

导出的地图只用于 Train 回放检查。若训练需要相近地形或道具，应在 Train 中实现可复制的内置场景，
并记录它和显示地图的差异。

**阶段门槛：**地图可加载、出生点有效、视觉通过验收，物理挑战尺寸不超过动作实测上限。

## 阶段 4——盘点并选择动作

训练新策略前先复用已有能力：

- 行走和身体姿态用于接近与观察；
- `jumper.five_foot` 用于夹爪侧移动和交互；
- `gesture_hello`、`gesture_bow`、`gesture_paw`、`gesture_salute` 用于故事节点；
- 现有舞蹈用于庆祝；
- 只有在落地和中断约束可接受时才使用跳跃。

对每个故事节点记录：原样复用、通过已有控制调整节奏、重新训练，或需要新实现。检查关节限位、
非足触地、稳定性、进入/退出姿态，以及到下一节点的过渡。

**阶段门槛：**故事板的每一个节点都映射到已命名的任务/动作或明确限定的新开发项。

## 阶段 5——先验证物理交互，再增加自主性

使用尺寸和质量已知的刚性道具。增加感知或接近前，先在固定已知位姿验证最小物理闭环：

1. 停稳；
2. 建立接触；
3. 执行交互；
4. 停止；
5. 脱离；
6. 撤退。

当前家居道具路线采用低速刚体推送，因为接触夹取没有达到跨 seed 可靠性门槛。详细证据和下一门槛
记录在开发分支的 `tasks/jumper/five_foot/out/grasp_validation_summary.md` 和
`HANDOFF_DEEPSEEK.md`。

按以下顺序推进：

```text
固定已知位姿
→ 跨 seed 重复试验
→ 更长距离
→ 初始位姿容差网格
→ 接近和对准
```

记录成功次数、总次数、位移、横向误差、倾斜、滑移/拖动、停车、脱离、摔倒、非足触地和失败
原因。保留失败试次。硬件标称抓取重量不是可靠载荷结论，必须使用实测结果。

**阶段门槛：**物理闭环达到声明的多 seed 门槛，且没有隐藏重试或未标注辅助。

## 阶段 6——编排行为状态机

只有底层交互可靠后，才编排故事顺序。典型道具交互为：

```text
INTRO_MOTION
→ OBSERVE
→ APPROACH
→ STABILIZE
→ ALIGN
→ CONTACT
→ INTERACT
→ STOP
→ DISENGAGE
→ RETREAT
→ CELEBRATE
```

每个状态声明：

- 进入动作和预期姿态；
- 可测量成功守卫；
- 超时；
- 摔倒和非法接触响应；
- 操作者取消行为；
- 成功与失败的下一状态；
- 目标来自感知、仿真真值还是操作者择时。

控制名称必须来自 `controller/vocabulary.json`。任务本地含义写在 `controls.yaml`；模式切换和退出
写在 `deploy/manifests.json`；controller 安全和级联状态写在 `deploy/jumper.controller.toml`。
验证进入、正常退出、超时、中断和操作者断开。不得训练策略忽略命令消失；命令丢失必须回到安全
停止方向。

**阶段门槛：**完整顺序可以安全进入、完成、取消和失败退出。

## 阶段 7——联排，但不夸大集成程度

当前没有宿主能同时消费全部产物，因此分别运行并保留以下检查：

1. Design 中从规定视角预览选定皮肤；
2. Design 中预览地图及其内嵌默认显示机器人；
3. 在经过验证的物理设置中回放每个 Train 策略和交互；
4. 在兼容时使用导入地图做 Train 回放，同时记住它使用任务机器人；
5. 使用 `play --app` 或浏览器/宿主验证 controller、控制和过渡；
6. 只有每个来源片段都标明验证范围后，才剪辑故事视频。

合成视频可以表达目标体验，但不能暗示 Train 加载了皮肤，也不能暗示显示地图检查验证了策略物理。

**阶段门槛：**所有组件检查通过，最终展示准确说明其边界。

## 阶段 8——导出、打包和记录

按照 `deploy/README.md` 和 deploy skill 导出通过验收的 checkpoint 并构建 `.app`。使用
bundle-manual 流程翻译并打包中文手册。保存：

- Train commit、任务参数和 checkpoint SHA-256；
- Design commit、profile 以及 `.skin`/`.map` SHA-256；
- 仿真器/后端和物理参数；
- 控制和状态机版本；
- 逐试次结果和验收门槛；
- 成功和失败视频；
- 所有剧情辅助机制；
- 尚未解决的仿真和实机缺口。

**阶段门槛：**包、controller 参考、手册和证据都能从记录的 commit 与哈希复现。

## 阶段 9——真实硬件递进验证

把硬件当作新的验证层：

1. 不向电机总线发指令的板端与 bundle 预检；
2. 无道具的支撑姿态和模式切换检查；
3. 带急停的低速空载动作；
4. 在清空的测试区使用轻、软、可替换道具；
5. 逐步增加距离和载荷；
6. 最后才执行排练过的完整故事。

没有实测前，不得把仿真载荷、摩擦、成功率或间隙结论转移到硬件。
